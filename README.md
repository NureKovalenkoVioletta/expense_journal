# expense_journal

Лабораторна робота 2 "Об'єктно-орієнтована модель предметної області".

Програму з ЛР1 переписано на класи: розбір, перевірка й агрегація витрат лишилися, але працюють з об'єктами предметної області, а не із записами (records) і рядками.

## Запуск

```
dart run
dart analyze
```

Потрібен Dart SDK 3.13.4 або новіший (первинні конструктори з'явилися в Dart 3.13).

## Структура програми

| Файл | Призначення |
|---|---|
| `bin/expense_journal.dart` | Точка входу: викликає бібліотеку й виводить результати за розділами |
| `lib/expense_data.dart` | Вхідні дані – константа `rawExpenses` (18 рядків, із них 3 пошкоджені та 2 з недопустимими значеннями) |
| `lib/expense.dart` | Клас-сутність `Expense` і розширення `ExpenseTotals` |
| `lib/payment.dart` | Запечатана ієрархія способів оплати `Payment`, домішка `MaskedNumber`, функція `paymentKind` |
| `lib/currency.dart` | Перелічення `Currency` з кодом і курсом валюти |
| `lib/repository.dart` | Інтерфейс `Identifiable` і узагальнене сховище `Repository` |
| `lib/expense_journal.dart` | Функції обробки з ЛР1 (валідація, конвеєри, групування, сортування, звіт, замикання) і класифікація витрат; реекспортує решту файлів `lib/` |

Логіка лежить у `lib/`, у `bin/` – лише виведення. Кожен тип предметної області винесено в окремий файл, щоб кожен файл відповідав за одне поняття. `bin/` імпортує лише `expense_journal.dart` і `expense_data.dart`: решту файлів `lib/` реекспортує `expense_journal.dart`. Каталогу `test/` немає: модульні тести вимагаються з ЛР3.

## Вибір типів даних

- **Клас `Expense` замість запису (record).** Незмінний: усі поля `final`, конструктор константний. Поля оголошено первинним конструктором (`class const Expense({...})`), тому кожне ім'я записано один раз. Обчислювані властивості (`amountInUah`, `ageInDays`, `isCardPayment`, `isoDate`, `id`) – гетери, вони не зберігаються.
- **`fromCsv`, `tryParse` і `cached`.** `Expense.fromCsv` – фабричний конструктор, що кидає `FormatException` на пошкодженому рядку: конструктор не може повернути `null`. Для журналу, де пошкоджені рядки – норма, використовується статичний `tryParse`, що повертає `null`, тож try/catch не потрібен. Фабрика `cached` повертає той самий екземпляр для того самого рядка.
- **`==` і `hashCode`.** Перевизначено разом, обидва за всіма шістьма полями, щоб рівні витрати мали однаковий хеш і не дублювалися в `Set` і `Map`.
- **Поля `currency` і `payment` лишилися рядками.** Розпізнані значення дають гетери `knownCurrency` і `paymentMethod`, які повертають `null` для невідомого значення. Так рядок із непідтримуваною валютою чи неправильним номером картки проходить розбір і відхиляється валідатором, як і в ЛР1.
- **Запечатаний клас `Payment`** з підтипами `CashPayment`, `CardPayment`, `TransferPayment`. Набір способів оплати закритий, тому `switch` за підтипами в `paymentKind` обходиться без `default`, а компілятор перевіряє його повноту. Поліморфний гетер `masked` кожен підтип реалізує по-своєму.
- **Домішка `MaskedNumber on Payment`.** Маскування номера потрібне картці й переказу, але не готівці. Успадкування не підходить: довелося б вставити в запечатану ієрархію проміжний абстрактний клас заради одного гетера, а `extends` у класу лише один. `on Payment` обмежує домішку підтипами `Payment` і дає змогу перевизначити `Payment.masked`.
- **Розширення `ExpenseTotals` на `Iterable<Expense>`.** Сума в гривнях потрібна в трьох функціях; розширення замінює однаковий ланцюжок `map` + `fold` і діє лише на колекціях витрат.
- **`Repository<T extends Identifiable>`.** Обмеження гарантує, що в кожного елемента є `id`, тому сховище звертається до `item.id` без приведення типів і без `dynamic`, а `Repository<String>` не компілюється.
- **Перелічення `Currency`.** Валюта має закритий набір значень; код і курс зберігаються в самому значенні, метод `toUah` перераховує суму. Замінює `switch` за рядком і множину підтримуваних валют з ЛР1.
- **Запис `({double min, double max, double average})`** лишився результатом статистики; у `bin/` його розібрано деструктуризацією `final (:min, :max, :average) = ...`.
- **`double` для суми.** Для навчального прикладу точності достатньо, суми виводяться з округленням до двох знаків. Для реальних фінансових розрахунків доцільніше зберігати суму в копійках (`int`).
- **`final DateTime referenceDate = DateTime(2026, 11, 1)`.** Фіксована дата замість `DateTime.now()`, щоб вивід не залежав від дня запуску. `final`, а не `const`, бо конструктор `DateTime` не є константним.

Залежностей часу виконання немає.

| Залежність | Тип | Навіщо | Розглянуті альтернативи |
|---|---|---|---|
| `lints` ^6.0.0 | dev | Набір правил `package:lints/recommended.yaml` для `dart analyze` (вимога методички) | `core.yaml` – слабший за вимогу; `flutter_lints` – призначений для Flutter-проєктів |
| `test` ^1.25.6 | dev | Модульні тести, обов'язкові з ЛР3; додано шаблоном `dart create` | Альтернатив у стандартній екосистемі Dart немає |

Пакет `collection` не підключено: групування виконано через `fold` із `putIfAbsent`, пошук – через `firstOrNull` з `dart:core`.

## Оператор `!`, `late`, `dynamic`

У коді не використовуються. Місця, де вони могли б з'явитися, розв'язано інакше:

- у `Payment.tryParse` значення іменованої групи (`String?`) береться шаблоном `case final number?`, а не оператором `!`;
- у `operator ==` тип `other` звужується перевіркою `other is Expense`, без приведення `as`;
- у `Repository` доступ до `id` дає обмеження `T extends Identifiable`, а не `dynamic`;
- `amountInUah` обробляє невідому валюту через `?.` і `??`, а результати `tryParse` перевіряються на `null`, після чого тип звужується автоматично.
